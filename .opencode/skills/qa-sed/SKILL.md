# QA / Security SED

Контроль качества и безопасности Фазы 6 (README п.6), оптимизация под НФТ (README п.5).

## Железные правила

- Негативные сценарии: 403 вне групп, дубли ФИО (в т.ч. «связь не подтверждена» — 422 с
  действием, не «нет в AD»), несколько записей AD с одним ФИО (пакетное подтверждение не
  снимает неоднозначность), просрочка TTL (`approval_ttl_days`), лимиты скана
  (`scan_retention_days/scan_max_mb`), rate-limit логина.
- «Нет записи в 1С/AD, нет delete»: вызовов записи нет, `AD_WRITE_ENABLED=false` не тронут,
  `audit_log` полный (append-only: UPDATE запрещён всем, DELETE — только для истории уже
  удалённой заявки, миграция 0021). Автосвязка и подтверждение связок пишут
  ТОЛЬКО в локальную БД (`link_1c_ad`, `users`, `employee_base_map`, `employees`,
  `link_discrepancies`) — проверять журналом/снапшотом БД, не обращениями к AD/1С.
- Кадровые данные: уволенные (`dismissal_date <= сегодня`) не выдаются в поиске и не участвуют
  в сопоставлении; метки регламентов (`hr_dismissals_synced_at`, `ad_links_synced_at`) пишутся
  только после успешного прохода.
- ПДн по ролям: отпуск и чувствительные поля — только ОК, владелец — урезанная карточка, поиск — по своим правам (README п.1). `fio` и `department` заявки видны **всем** (решение человека 2026-10-14), `tab_num`/`enterprise`/`enterprise_name`/`employee_key`/`assignee`/`created_by`/`done_by` — только привилегированным. Маска «Сотрудник № …» в интерфейсе — только на заявках без ФИО.
- Замещение: заместитель видит шаг оригинала и отмечает его, но только со своим блоком `step_decide` и в интервале записи; в `audit_log`/`approvals` — логин заместителя. Замещение действует на КАЖДОМ шаге, включая ГРУППОВОЙ (оба режима шага), состав группы-владельца — из кэша `ad_group_members`. Негативные тесты: без блока `step_decide` 403, истёкшая/ещё не начавшаяся запись 403, чужая пара логинов 403, повторная отметка заместителем 409, транзитивности (A→B, B→C) нет — C не действует за A; заместитель участника ГРУППОВОГО шага действует при наполненном/синхронизированном кэше `ad_group_members` и НЕ действует при пустом или недоступном кэше (fail-soft); заместитель видит бланк и вложения заявки так же, как замещаемый (`documents._can_view`/`attachments._can_access` зовут `requests._is_step_viewer`), но сама печать `POST /requests/{id}/print` без блока `print_blank` — 403 (замещение блок функций не даёт).
- **Личный раздел заместителей (решение человека 2026-10-15) — негативные проверки:**
  - `GET/PUT/DELETE /api/substitutes/my/{id}` на **ЧУЖУЮ запись — 404**, одинаково как на
    отсутствующую (не 403 и не 409: иначе по коду ответа утекает, что запись с таким id
    существует). Проверять именно код ответа И тело, а не только «изменений нет».
  - `principal_sam` в теле личной ручки (`POST/PUT /api/substitutes/my`) — **422**
    (логин оригинала всегда из сессии); заместитель «сам себе» — **422**; та же пара —
    409; хранилище недоступно — 503.
  - `GET /api/substitutes/candidates?q=` короче 2 символов — **422**; сам сотрудник в
    выдаче отсутствует; уволенных (`dismissal_date`) нет.
  - `GET /api/settings/substitutes` у сотрудника без блока `settings_substitutes` — **403**,
    а `GET /api/substitutes/my` — **200** (личный контур блоков не требует).
  - `/api/ad/search` у сотрудника остаётся **403** (блок `employee_directory`): новая
    видимость ФИО сотрудников (решение человека 2026-10-15) даёт только
    `GET /api/substitutes/candidates` и объём `sam`/`fio`/`department`/`position`.
  - Аудит личных операций: события `substitutes.create/update/delete`, `entity=substitute`,
    в `details` только срок и признак писем — логинов и ФИО нет.
- НФТ: TLS 1.2+, HSTS, сессии 15–20 мин, RPO 24ч/RTO 4ч (уточнить к тесту), `pg_dump` + снапшот.

## Приемка правки

Чек-лист Фазы 6 закрыт, негативные тесты зелёные, `audit_log` полный.
