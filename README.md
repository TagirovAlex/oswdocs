# OSWDocs — Система электронного документооборота (СЭД)

## Введение

OSWDocs — система электронного документооборота для автоматизации процессов обработки заявлений и документов с ролевой моделью доступа, интеграциями с Active Directory (LDAPS), 1С ЗУП (OData) и корпоративной почтой. Проект развёртывается в среде Docker/Compose под Linux.

## Назначение

Назначение системы — организация электронного документооборота, маршрутизация заявок по процессам, контроль сроков согласования, хранение вложений, ведение аудита действий пользователей.

Основные блоки:

- **Бланки и маршрут** — справочник бланков: бланк = упорядоченный набор СВОИХ шагов
  (текст шага, вид исполнителя и согласующие задаёт сотрудник ОК, этап справочника шагу не нужен);
  шаги можно брать готовыми из **справочника шагов** (`step_catalog`) — выбранный шаг
  копируется в состав бланка и правится там независимо; бланк выбирает сотрудник ОК при
  создании заявки, в заявку пишется снимок бланка и его шагов.
  Подбор по профилю службы (данные сотрудника, служба, руководитель — из AD) остался запасным
  путём за настройкой `blank_autopick` (по умолчанию выключен), ручной конструктор — альтернатива.
- **Справочник сотрудников** — ежедневная синхронизация из 1С, даты увольнения из регистра кадровых
  данных, уволенные скрыты; поиск работает по локальной таблице.
- **Сопоставление 1С↔AD** — автосвязка по ФИО, разбор дублей по должности/службе из регистра,
  выдача расхождений и массовое подтверждение; ручной запуск и регламент по расписанию.
- **Заместители (замещение по шагам)** — локальный справочник «сотрудник → его
  заместитель(и)» с интервалом действия (`valid_from` обязателен, `valid_to` пуст —
  действует, пока не отменят). Заместитель видит шаги оригинала и может поставить
  согласование или отказ за него, если у него есть право «Отметки по шагам»; в истории
  шага и в аудите — ФИО заместителя. Отдельного признака «за кого» не заводится.
  Замещение действует на **каждом** шаге, включая **групповой**: если сотрудник —
  участник группы-владельца шага, его заместитель действует за него (состав группы
  берётся из кэша `ad_group_members`; кэш недоступен или не синхронизирован — замещение
  на таком шаге не проверяется). Это касается обоих режимов шага (`sequential`
  и `parallel`).
  Копию письма «назначена» заместитель получает, если у него в записи включён флаг
  «слать письма» (по умолчанию включён); для группового шага письмо получают и
  заместители участников группы-владельца.
  **Карточку заявки видит каждый участвующий в согласовании** (решение человека
  2026-10-15): инициатор, владелец шага (в т.ч. через группу AD, реестр этапа или
  заместителя) и тот, кто уже согласовал. Прежнее правило «карточка видна только
  владельцу шага» оставлено в силе только для **вложений** (решение человека
  2026-10-15: «бланк — все участвующие, вложения по рекомендации»).
  Сама печать бланка требует блока прав «Печать бланка» (`print_blank`).
  **Записи заводит сам сотрудник** в личном разделе «Заместители» — вкладка
  сразу после «Заявки», без блоков прав, доступна любому вошедшему. Раздел
  показывает и правит ТОЛЬКО собственные записи «я → мой заместитель».
  Заместителей у сотрудника может быть несколько, но не больше **лимита
  заместителей** — инфраструктурной настройки `substitute_deputies_limit`
  (целое положительное, дефолт **3**; правит администратор на вкладке «Инфра»,
  сид — миграция 0025). Считаются только записи, **действующие на сегодня**
  (законченные и ещё не начавшиеся место не занимают), превышение — 422 с именем
  ключа настройки. Заместителя выбирают **модалкой подбора** из локального
  справочника сотрудников
  (`GET /api/substitutes/candidates?q=&page=&page_size=`: `sam`/`fio`/`department`/
  `position`, самого сотрудника исключает, `q` короче двух символов — 422).
  Администратор и администратор СЭД управляют **всеми** записями через ту же
  вкладку «Заместители» в настройках (блок прав `settings_substitutes`) — это
  вторая точка входа в один справочник, а не другой справочник.
  Видимость ФИО сотрудников в подборе заместителя — **решение человека
  2026-10-15**: локальный справочник сотрудников открыт на чтение всем вошедшим
  в объёме `sam`/`fio`/`department`/`position`; `/api/ad/search` под блоком прав
  `employee_directory` остался как был.
- **Печать бланка** — документ собирается из данных заявки (`python-docx`) единой вёрсткой
  (макета/пресетов нет), шапка, подвал и текст шага берутся из снимка бланка; в шапке/подвале/шаге
  подставляются плейсхолдеры (`{fio}`, `{date}`, `{manager}` и др.); QR на заявку; каждый шаг
  печатается отдельным блоком строк (номер, название с режимом «последовательно/параллельно»,
  текст, все ответственные, отметка/дата).

## Терминология

- **СЭД** — система электронного документооборота.
- **Заявка (Request)** — единица документооборота с определённым маршрутом согласования.
- **Маршрут (Route)** — последовательность шагов согласования.
- **Шаг согласования (Approval Step)** — этап маршрута с назначением ответственных.
- **Аудит (Audit Log)** — журнал событий системы.
- **Ролевая модель** — разграничение прав доступа по ролям.
- **Связка 1С↔AD** — подтверждённое соответствие карточки сотрудника в 1С и учётной записи в AD;
  источник подразделения, должности и руководителя для маршрута.
- **Сопоставление (автосвязка)** — проход, который связывает сотрудников по точному ФИО;
  несвязанное складывается в **расхождения** (`one_c_duplicate` — несколько карточек ФИО в 1С,
  `ad_duplicate` — несколько записей ФИО в AD, `not_in_ad` — нет записи в AD) и подтверждается
  администратором поштучно или пакетом (раздел «Сопоставление 1С↔AD»).
- **Кадровые данные (регистр)** — текущие кадровые данные 1С (подразделение, должность, дата
  приёма, **дата увольнения**); читаются постранично, обновляются ежедневно. Увольнение
  определяется только 1С — учётку в AD после увольнения отключают вручную.
- **Профиль маршрута** — набор этапов, подбираемый по службе сотрудника (запасной путь за
  `blank_autopick`); **служба** берётся из AD.
- **Бланк** — элемент справочника заявок: код, название, вид документа (классификация), шапка
  (`header_html`, визуальный редактор TipTap), подвал (`footer_lines`), активность и состав шагов.
  Бланк выбирает сотрудник ОК при создании заявки. У шага бланка может быть **свой срок в часах**
  (`blank_steps.ttl_hours`, миграция 0026) — задаётся в настройках, вкладка «Бланки», в карточке
  шага (поля «Срок шага» и «Единица срока»; пусто — общий срок `approval_ttl_days` из настроек,
  дни пересчитываются в часы). В справочнике шагов (заготовках для бланков) срока нет.
  Выданному шагу срок пишется в снимок заявки, поэтому переоткрытие и повтор считают его по
  снимку, а не по справочнику.
- **Заместитель** — сотрудник, которому делегировано право действовать за ответственным
  шага (согласовать или отказать): за персональным ответственным (снимок `assignees`,
  в том числе состав этапа-реестра — он пишется в тот же снимок) и за участником
  группы-владельца группового шага (состав группы — из кэша `ad_group_members`,
  имя группы должно совпадать с кэшем точно; при пустом или недоступном кэше замещение
  на групповом шаге не проверяется). Шаг при этом остаётся назначенным оригиналу;
  отметка, история и аудит — от логина заместителя. На групповом шаге одну отметку
  закрывает шаг целиком — как и любой отметкой участника группы. Запись действует
  в интервале дат и заводится **самим сотрудником** в личном разделе «Заместители»
  (`substitutes`, ручки `/substitutes/my` — без блоков прав, только свои записи;
  чужая запись отвечает 404, чтобы не выдать её существование), а администратор
  и администратор СЭД правят весь справочник в настройках (блок прав
  `settings_substitutes`). Число **одновременно действующих** записей сотрудника
  ограничено настройкой `substitute_deputies_limit` (дефолт 3).
  **Участник согласования** — тот, кто имеет право видеть карточку заявки помимо
  привилегированных ролей: инициатор, владелец шага (персональный ответственный,
  участник группы-владельца, участник состава этапа, заместитель ответственного)
  и оставивший отметку по любому шагу (`requests._is_participant`/`_has_own_mark`).
  **Бланк** видят все участники согласования наравне с владельцем шага, а
  **вложения** остались у владельца шага, его заместителя, ОК и админов
  (`attachments._can_access` — решение человека 2026-10-15). Печать бланка в обоих
  случаях остаётся за блоком прав «Печать бланка» (`print_blank`).
- **Шаг бланка** — самостоятельный шаг, этап справочника ему не нужен: порядок (`step_order`),
  название (`title`), текст шага (`stage_lines`), вид исполнителя (`executor_kind`: `people` —
  список согласующих, `ad_group` — группа AD, `manager_ad` — руководитель сотрудника), логины
  согласующих (`assignees`), группа AD (`owner_group`), режим шага (`approval_mode`), флаги
  `optional`/`require_comment`. Снять шаг бланка сотрудник ОК может по номеру шага
  (`dismissed_step_orders`), не по коду этапа.
- **Шаг справочника (`step_catalog`)** — переиспользуемая заготовка шага бланка (те же поля,
  плюс код и активность). Справочник правится админом во вкладке «Шаги»; в составе бланка шаг
  из справочника берётся копией («Взять из справочника») и правится уже в бланке независимо.
- **Ответственные шага** — снимок логинов на момент выдачи заявки (`request_steps.assignees`);
  у группового шага персональных исполнителей нет, действует группа AD.
- **Режим шага** — `parallel` («кто-то один»: закрывает любой из ответственных) или `sequential`
  («все ответственные», режим по умолчанию). Задаётся сотрудником ОК в составе бланка; в печати
  помечается у каждого шага («последовательно»/«параллельно»).
- **Снимок бланка в заявке** — `blank_id/blank_name/blank_version/blank_header_html/
  blank_footer_lines` плюс тексты, ответственные, режим и признак «шаг можно снять» каждого шага:
  правка справочника не меняет уже выданные заявки.
- **Плейсхолдеры печати** — `{fio}`, `{position}`, `{department}`, `{tab_num}`, `{enterprise}`,
  `{blank_name}`, `{subject}`, `{content}`, `{date}`, `{dismissal_date}`, `{steps}`, `{manager}`:
  подставляются в шапку, подвал и текст шага, значения печатаются текстом (не разметкой),
  неизвестный плейсхолдер остаётся текстом.
- **Справочник этапов** (`approval_stages`, `stage_assignees`, `route_profiles`) — не удалён:
  на нём держится запасной подбор маршрута по профилю службы за `blank_autopick`, и этапы
  этого профиля снимаются/добавляются по кодам (`dismissed_stages`/`added_stages`).

## Конфигурация и запуск

1. Скопируйте .env.example в .env и заполните параметры.
2. docker compose config.
3. docker compose up --build -d.

Секреты только в .env, файл не коммитится.

## Разработка и прод (разделение compose)

- `docker-compose.yml` — прод-база (образы, именованные тома, `frontend_dist` для статики).
- `docker-compose.override.yml` — только локальная разработка (bind-mount `./api/app`,
  `./frontend/dist`, `--reload` у `api`). Подхватывается автоматически любой голой
  командой `docker compose ...`.
- На прод-ВМ (`/srv/sed`) override применяться не должен: запуск только с явным `-f`
  (`docker compose -f docker-compose.yml up -d --build`; при разъезде БД добавить
  `-f docker-compose.prod-db-external.yml` и `--scale db=0`). Иначе прод подхватит
  dev-монтирования (пустой host-`dist` даёт 403 от proxy).

## Безопасность

- AD_WRITE_ENABLED=false по умолчанию; в 1С и AD система пишет только на чтение (запись — исключительно
  в локальную БД: связки, справочники маршрута, бланки, расхождения, аудит)
- Права — блоками функций (миграция 0020): резолв по группам AD, fail-closed при недоступном
  справочнике, запрет снятия прав у себя (409); роль в сессии — производная от совпавших блоков
- Ролевая модель доступа: ПДн заявки обрезаются у владельца (табельный номер,
  предприятие, ключ сотрудника), полная карточка — ОК/админ; исключение — ФИО и служба
  заявки видны всем (решение человека 2026-10-14: без них согласующий не понимает,
  о ком заявка)
- **Видимость карточки — по участию в согласовании, а не только по владению шагом**
  (решение человека 2026-10-15, `requests._is_participant`): карточку видят
  привилегированные роли, **инициатор**, **владелец шага** (персональный
  ответственный, участник группы AD, участник состава этапа, заместитель) и
  **любой, кто уже согласовал** (`_has_own_mark` — логин в `approvals` любого шага).
  Чем отличается от прежнего правила: раньше доступ к карточке давал только владелец
  шага, поэтому её не видели инициатор, который не был согласующим, и сотрудник ОК,
  оставивший отметку, если ему потом переназначали его шаг. Правило применено в трёх
  местах: ветка «мои» списка заявок, счётчик папки «Мои задачи» и гейт карточки —
  они не расходятся.
  **Бланк** (`documents._can_view`) видят все участники согласования наравне с
  владельцем шага (список ролей прежний: ОК/руководители ОК/админ; администратор
  СЭД в бланк не входит — `_is_participant(include_privileged=False)`).
  **Вложения не менялись** (`attachments._can_access`): владелец шага, его
  заместитель, ОК и админы — «бланк — все участвующие, вложения по рекомендации».
  Печать бланка в обоих случаях остаётся за блоком `print_blank`.
  **Оговорка про ПДн:** обрезание ПДн касается карточки (`_public_view`), а сам
  бланк — это ПДн: в нём текстом идут ФИО, табельный номер, предприятие,
  должность и данные об отпуске (`GET /documents/{id}/pdf` отдаёт сам файл).
  Решение человека 2026-10-15 («бланк — все участвующие в согласовании»)
  расширяет круг тех, кому этот файл доступен; в карточке заявки у участника
  табельный номер и предприятие по-прежнему `null`.
- Число заместителей у сотрудника ограничено настройкой `substitute_deputies_limit`
  (целое положительное, дефолт 3, ключ `INFRA_KEYS`, вкладка «Инфра», сид — миграция
  0025); превышение — 422 с именем ключа. При недоступном или битом значении, а
