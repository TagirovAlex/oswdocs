# Шаблоны СЭД: переменные и как их вставлять

Обновлено: 2026-10-06. Источник истины — код (`api/app/docs.py`, `api/app/mailer.py`,
`api/app/documents.py`, `api/app/routing.py`); тексты шаблонов хранятся в `settings` БД
(не в коде), исходные бланки — `office.docx`/`line.docx` в корне репозитория.

## Как вставлять переменные

Шаблоны используют **Jinja2-синтаксис** — переменная пишется в двойных фигурных скобках:

```
{{ fio }}
{{ request_id }}
```

- Внутри `{{ }}` — имя переменной (без `$`, без `%`).
- Пустые значения подставляются как пустая строка.
- Многострочный текст/тело письма можно собирать обычными строками шаблона.
- Вложенные условия/циклы Jinja2 (`{% if %}`, `{% for %}`) — по стандарту Jinja2,
  но для бланков используйте простые подстановки (docxtpl рендерит строки шаблона).

## 1. Бланки бегунка (`doc_templates`)

Настройка: `settings.doc_templates` — список `{service, category, body, file?, position_set?}`.
Подбор шаблона: служба (`department`) + категория заявки + набор должностей.
Пустые служба/категория в записи — wildcard (бланк только по набору — для
ручных заявок без категории). Среди подходящих приоритет — бланку, чей набор
(`position_set` → `settings.position_sets`) содержит должность сотрудника
(сравнение без учёта регистра/пробелов); иначе — бланк без набора
(по умолчанию); иначе — ручной конструктор. Без должности — первый
подходящий (прежнее поведение).

**Вид бланка (`office`/`line`)** задаётся служебой заявки, а не категорией:
`documents._blank_kind` берёт `blank_kind` службы из справочника `ad_services`
(миграция 0008, наполняется синком подразделений AD) и приоритетнее категории заявки:
`position_to_category` заполняется вручную и на стенде пуст, а признак службы
приезжает из AD. Служба не определена — печатается `office`-бланк по умолчанию
(бумага ОК нужна всегда; тихий текстовый фолбэк выглядел бы поломкой), в ответе
печати возвращается `blank_kind`.

**Исходники и файлы.** `office.docx` и `line.docx` в корне репозитория — эталон
макета (шапка/строки/подвал, QR слева вверху, данные сотрудника справа). Из них
генерируются производные бланки с динамической таблицей шагов
(`FILES_DIR/templates/office_base.docx`, `line_base.docx`); в `doc_templates`
хранится только имя файла (`file`). Текстовый `body` — фолбэк, если файла нет.

Наборы должностей: `settings.position_sets` — список `{name, positions}`
(названия справочника «Наборы должностей»; подсказки — `GET /api/ad/titles`:
титулы AD из кэша + должности из локального справочника employees —
обратный приоритет действует только здесь, везде иначе истина — 1С).

- `body` — текстовый шаблон (фолбэк; рендерится docxtpl из строк).
- `file` — (необязательно, задача H) имя `.docx`-файла в `FILES_DIR/templates/`:
  НАСТОЯЩИЙ бланк, вёрстка (шапка/строки/подвал/таблицы) живёт в файле. Если `file`
  задан и файл есть на диске — рендер из файла, иначе текстовый `body` (не ломать).
- Редактирование .docx — в Word; в панели администратора — импорт/скачивание/замена/предпросмотр.

Доступные переменные:

| Переменная      | Значение                                   |
|-----------------|--------------------------------------------|
| `{{ request_id }}` | Номер заявки (например `REQ-0001`)        |
| `{{ fio }}`        | ФИО сотрудника (из 1С / ручного ввода)     |
| `{{ department }}` | Подразделение/служба (поле 1С)             |
| `{{ position }}`   | Должность (поле 1С)                        |
| `{{ category }}`   | Категория заявки (пусто, если не задана)   |
| `{{ enterprise }}` | Предприятие (код/имя из настроек)          |
| `{{ steps }}`      | Список шагов маршрута: `{order, owner, status, position, assignee, fio, stage_lines, done_at}` — в .docx-файле строки таблицы через `{%tr%}` (см. ниже) |
| `{{ qr }}`         | QR с URL заявки: в .docx-файле — текстовый маркер `{{ qr }}`, при рендере на его место подставляется картинка (30x30 мм) |

Поля шага:

| Переменная               | Значение                                                         |
|--------------------------|------------------------------------------------------------------|
| `{{ step.order }}`       | Порядковый номер этапа                                            |
| `{{ step.owner }}`       | Логин исполнителя (персональный) или группа AD                    |
| `{{ step.status }}`      | Статус шага                                                       |
| `{{ step.position }}`    | Название этапа из справочника (для колонки «Должность»)           |
| `{{ step.assignee }}`    | Логин персонального исполнителя (пусто у группового этапа)         |
| `{{ step.fio }}`         | ФИО исполнителя из зеркала AD; пусто — дописать от руки            |
| `{{ step.stage_lines }}` | Список пунктов этапа (снимок `stage_lines`) — строки через `{%p %}` |
| `{{ step.done_at }}`     | Отметка выполнения текстом (пусто, если не выполнен)               |

ФИО исполнителя подставляет `documents._fill_step_fio` по логину (`assignee`) из
зеркала `users`; у группового этапа логина нет — колонка остаётся пустой, её
заполняют от руки, как в исходных бланках. `stage_lines` приходят из справочника
этапов (снимок на момент создания заявки).

Строки таблицы шагов в .docx-шаблоне (docxtpl): `{%tr for step in steps %}` и
`{%tr endfor %}` — **в отдельных строках таблицы** (в одной строке две метки
docxtpl не понимает: строка удаляется целиком, рендер падает с ошибкой шаблона).
Строка с данными `{{ step.order }}` / `{{ step.owner }}` / `{{ step.status }}` — между ними:

```
| №    | Владелец шага      | Статус            |
| {%tr for step in steps %} |                 |                    |   <- строка-метка, в рендере исчезает
| {{ step.order }} | {{ step.owner }} | {{ step.status }} |   <- повторяется по шагам
| {%tr endfor %} |                 |                    |   <- строка-метка, в рендере исчезает
```

Пункты этапа (`stage_lines`) — вложенным циклом по абзацам ячейки, метки `{%p %}`
тоже в отдельных абзацах:

```
| {%tr for step in steps %} |                 |                    |   <- строка шага
| {{ step.order }} | {%p for line in step.stage_lines %}{{ step.position }}: {{ line }}{%p endfor %} | {{ step.done_at }} |
| {%tr endfor %} |                 |                    |
```

Пример текстового тела бланка (`body`):

```
БЕГУНОК УВОЛЬНЕНИЯ
Сотрудник: {{ fio }}
Подразделение: {{ department }}
Должность: {{ position }}
Номер заявки: {{ request_id }}
Предприятие: {{ enterprise }}
```

## 2. Шаблоны писем (`mail_templates`)

Настройка: `settings.mail_templates` — список `{code, subject, body_html}`.
`code` — событие: `assigned` (назначена), `reminder`, `escalation`, `returned`,
`closed` и т.д. (см. `mailer.py`).

Доступные переменные:

| Переменная       | Значение                                        |
|------------------|-------------------------------------------------|
| `{{ request_id }}` | Номер заявки                                  |
| `{{ fio }}`        | ФИО сотрудника                                |
| `{{ url }}`        | Ссылка на заявку (для перехода из письма)     |
| `{{ event }}`      | Код события (служебное)                        |

Пример:

```
Тема: Назначена {{ request_id }}
Тело: Заявка {{ request_id }} назначена вам на согласование.
      Сотрудник: {{ fio }}.
      Открыть: {{ url }}
```

## 3. Маршруты: справочники и конструктор

Маршрут заявки собирается по справочникам (миграция 0008), а не по текстовым шаблонам:

- `ad_services` — службы (`dept_name` из AD, активность, `blank_kind`, профиль по умолчанию);
- `approval_stages` — этапы: название, `owner_kind` (`ad_group` — группа AD, `stage_roster` —
  реестр в СЭД, `manager_ad` — руководитель сотрудника из AD), `stage_lines` (пункты этапа),
  флаги `optional`/`require_comment`, признак печати исполнителя;
- `stage_assignees` — состав этапа для `stage_roster`; пустой реестр помечает этап
  заблокированным («Не задан состав этапа»);
- `route_profiles` + `route_profile_steps` — профили маршрутов по службам и порядок этапов.

При создании заявки профиль подбирается по службе сотрудника из AD
(`route_mode=auto`), снятые на форме этапы уходят в `dismissed_stages`, добавленные —
в `added_stages`. В заявку пишется снимок подбора (профиль, служба, этап, строки,
код шага профиля), поэтому позднейшая правка справочников не меняет выданный маршрут.
`route_mode=custom` — ручной конструктор ОК (режим блока, исполнители-группы/сотрудники);
исполнители ищутся в AD, группы берутся из настроек.

Прежние `settings.templates`/`template_steps`/`template_filters` в подборе не
участвуют: после миграции 0008 это пустые таблицы (совместимость), а
`position_sets`/`position_to_category` остались только для бланков.

## Примечания

- Переменные подставляются **без ПДн сверх нужного**: бланк и письмо получают только
  перечисленные поля; ФИО владельцу-согласующему приходит (он участник процесса).
- Если шаблон отсутствует или его переменная не найдена — подставляется пусто,
  ошибкой не считается.
- Менять наборы переменных можно только вместе с кодом (контракт) — см. AGENTS.md §3.
- Этап без состава исполнителей (`stage_roster` с пустым `stage_assignees`) печатается
  с пустой колонкой «Должность/ФИО» и помечается в интерфейсе как заблокированный —
  состав заполняет администратор в справочниках маршрута.
