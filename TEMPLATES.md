# Бланки, этапы и письма СЭД: как устроено и что уходит в печать

Обновлено: 2026-10-16. Источник истины — код (`api/app/requests.py`, `api/app/routing.py`,
`api/app/routing_store.py`, `api/app/settings_routes.py`, `api/app/documents.py`, `api/app/docs.py`,
`api/app/mailer.py`) и миграции `db/alembic/versions/0012_blank_directory.py`,
`0013_multi_assignee_steps.py`, `0014_blank_steps_own.py`, `0015_step_optional.py`,
`0016_drop_dead_setting_keys.py`, `0017_blank_steps_drop_dead_columns.py`,
`0018_step_catalog_and_layout_cleanup.py`, `0026_step_ttl_hours.py`.

Ключевая мысль модели: **оформление бланка — не файл, а данные**. Файлы-шаблоны `.docx`
(`office.docx`/`line.docx` и производные) удалены из проекта, настройки `doc_templates`/
`position_sets` и их ручки тоже. Документ печати собирается из заявки и снимка бланка.

Вторая ключевая мысль (миграция 0014): **шаг бланка — самостоятельный шаг, а не этап
справочника**. Состав бланка (текст шага, согласующие, группа AD, руководитель), шапка и подвал
задаёт сотрудник ОК через админку; справочник этапов для этого не нужен и остался запасным
путём подбора маршрута по службе.

## 1. Бланк (справочник `blanks`, миграция 0012)

Бланк — элемент справочника заявок. Его выбирает сотрудник ОК при создании заявки; бланк
задаёт состав шагов и ответственных.

| Поле        | Значение                                                        |
|-------------|-----------------------------------------------------------------|
| `code`      | Код бланка (`^[a-z][a-z0-9_]*$`, уникален; дубль — 409)          |
| `name`      | Наименование бланка (видно сотруднику ОК в селекте)             |
| `doc_type_code` | Вид документа (`doc_types.code`) — классификация, на печать не влияет |
| `description` | Пояснение для сотрудника ОК (подсказка селекта)              |
| `header_html` | Шапка бланка (HTML визуального редактора TipTap), печатается абзацами |
| `footer_lines` | Подвал бланка — список строк печати (по центру после шагов); строка — HTML абзаца визуального редактора, печатается тем же разбором, что шапка |
| `active`    | `false` — бланк вне формы заявки (админка его правит, ОК не видит) |
| `version`   | Счётчик состава: растёт при каждой замене шагов                  |

Сид миграции: каждый вид документа `doc_types` становится бланком с тем же кодом и названием.
Макета печати у бланка нет (поле `layout` снято миграцией 0018): печать единая, пресетов
`office`/`line` больше нет. Перенос состава шагов из профилей маршрута НЕ выполнялся (у профилей привязка
к службам AD, у бланка — к виду документа) — состав собирает администратор. Миграция 0014 дополнительно
очистила содержимое `blanks`/`blank_steps` (прежние шаги ссылались на этапы и в новой модели смысла
не имеют): бланки собираются заново через админку.

Эндпоинты справочника (только `admin`, иначе 403; хранилище недоступно — 503):

| Метод и путь | Назначение |
|---|---|
| `GET /api/settings/routing/blanks` | Все бланки, включая отключённые; в каждой строке `step_count` |
| `POST /api/settings/routing/blanks` | Создать бланк (код уникален) |
| `PUT /api/settings/routing/blanks/{blank_id}` | Частичная правка (код неизменен) |
| `GET /api/settings/routing/blanks/{blank_id}/steps` | Собственные шаги бланка по порядку (без этапа) |
| `PUT /api/settings/routing/blanks/{blank_id}/steps` | Полная замена состава одной транзакцией, `version` растёт |

Аудит: `blank.create`, `blank.update`, `blank.steps.update`.

## 2. Шаг бланка (`blank_steps`, миграции 0012/0013/0014/0017/0026)

Шаг бланка самостоятельный: **этап справочника ему не нужен**, свой текст и своих согласующих
задаёт сотрудник ОК. Порядок уникален внутри бланка (в БД это PK `(blank_id, step_order)`,
дубль порядка — 422 на границе). Мёртвые колонки прежней модели `stage_id`,
`optional_override`, `require_comment_override` **удалены из таблицы миграцией 0017** (вместе с FK
на `approval_stages` и `UNIQUE (blank_id, stage_id)`) — в схеме их нет, API их не принимает и не
отдаёт. Сняты 0017; прежние значения при откате не восстанавливаются.

| Поле шага бланка | Значение |
|---|---|
| `step_order` | Порядок шага в бланке, с 1 |
| `title` | Название шага (печатается заголовком блока шага) |
| `stage_lines` | Текст шага — список строк; HTML TipTap допускается, доходит до печати. В админке набирается ОДНИМ визуальным редактором на шаг, в список делится по абзацам (формат хранения прежний) |
| `executor_kind` | Вид исполнителя: `people` (список согласующих), `ad_group` (группа AD), `manager_ad` (руководитель сотрудника в AD) |
| `assignees` | Логины согласующих (`executor_kind=people`) |
| `owner_group` | Группа AD (`executor_kind=ad_group`); группа сверяется со справочником групп шагов, иначе 422 |
| `approval_mode` | Режим шага: `sequential` («все ответственные», по умолчанию) или `parallel` («любой ответственный») |
| `optional` | Шаг необязательный: сотрудник ОК может снять его при выдаче заявки |
| `require_comment` | Комментарий обязателен даже при согласии |
| `ttl_hours` | Свой срок шага в часах (миграция 0026). `NULL` — общий срок `approval_ttl_days` из настроек. В админке поле ввода с переключателем «часов/дней»: дни пересчитываются в часы, хранится одна единица |

Пара «вид исполнителя ↔ исполнитель» проверяется на границе запроса (422): `people` — непустой
`assignees`, `ad_group` — непустой `owner_group`. У `manager_ad` без руководителя в AD маршрут не
собирается (422 с подсказкой задать замену `manager`); в предпросмотре такой шаг остаётся в ответе
с `blocked_reason`.

`optional` шага бланка попадает в снимок заявки (`request_steps.optional`, миграция 0015) — правка
справочника уже выданную заявку не меняет. У ранее выданных заявок дефолт `TRUE`: неизвестное
значение трактуется как «шаг можно снять», блокировки нет.

Срок шага — двумя ступенями: общий (`approval_ttl_days`, дней, настройка админки) и свой
(`ttl_hours`, часами, у шага бланка). Свой срок побеждает общий; при выдаче заявки он пишется в
снимок `request_steps.ttl_hours`, и переоткрытие/повтор шага считает новый срок по снимку, а не по
справочнику. Напоминание бегунка считается от своего срока шага (половина срока), у шага без своего
срока — от общего. У ранее выданных заявок `NULL`: срок считается как раньше, по общей настройке.

**Где задаётся.** Свой срок шага задаётся в админ-вкладке **«Бланки»**: выбрать бланк → в карточке
шага поля «Срок шага» и «Единица срока» (рядом с «Необязательный» и «Комментарий обязателен»).
Пустое поле = общий срок `approval_ttl_days`; в поле принимаются часы или дни (дни пересчитываются в
часы — в БД и в снимке заявки лежит одна единица, часы), переключатель единицы меняет только вид
значения, сам срок не трогает. Срок шага виден сотруднику ОК в предпросмотре маршрута
(`ttl_hours` в `RoutePreviewStageOut`) до создания заявки.

Общий срок задаётся отдельно: «Настройки» → вкладка с контентными настройками → «TTL отметок, дней
(approval_ttl_days)». Он применяется к шагам без своего срока и перечитывается на каждый вызов
(`get_route_settings`): смена настройки видна следующей выданной заявке, у уже выданных сроки в
`expires_at` не меняются. В справочнике шагов (вкладка «Шаги») срока нет — это заготовки, см. §2.1.

### Снятие шага бланка — по номеру

У шага бланка нет кода этапа, поэтому снимает его сотрудник ОК **по номеру шага**
(`dismissed_step_orders: list[int]` в `POST /requests/route/preview` и `POST /requests`) —
тем же номером, что задан в справочнике (`blank_steps.step_order`). Этапы профиля службы и ручного
маршрута по-прежнему снимаются и добавляются по кодам (`dismissed_stages`/`added_stages`).

Отказы (422, молчаливого пропуска нет):

| Причина | Ответ |
|---|---|
| Номер вне состава шагов бланка | перечень допустимых номеров |
| Номер у обязательного шага (`optional=false`) | номер и название шага |
| Сняты все шаги маршрута | требование вернуть хотя бы один шаг |

Причина подбора дополняется пометкой `DismissedStep=номера` (как `Dismissed=коды` у этапов).

### Правка маршрута и судьба отказавшего (`PATCH /api/requests/{id}/steps`)

Ожидающие шаги пересобираются из payload, закрытые сохраняются, снимок этапа
переносится на шаги с тем же исполнителем. Отказавший шаг (статус «отклонен»/«возвращен») в
маршрут не входит, и его судьбу сотрудник ОК решает в правке маршрута (решение человека
2026-10-12) — оба действия доступны:

| Поле | Что делает |
|---|---|
| `reopen_orders` | Шаг возвращается в маршрут: снова «ожидает», новый срок, отметки прежнего круга сняты (как при повторной подаче) |
| `drop_orders` | Шаг убирается из маршрута совсем — отказавшему больше не надо подписывать |

Ограничения: действовать можно только на отказавшие/возвращённые шаги (решение по согласованному
шагу не вытирается молча); один order нельзя указать в обоих списках (422); неизвестный order —
422. Действия пишутся в историю отдельно: `step.reopen`, `step.drop` (рядом с общим `steps.patch`).
Предпросмотр и создание используют один и тот же код проверки — предпросмотр не обещает маршрут,
который создание не примет.

Статусы шага в контракте — строки `api/app/requests.py` (`STEP_PENDING`, `STEP_APPROVED`,
`STEP_REFUSED`, `STEP_RETURNED`, `STEP_EXPIRED`). **Отказ — это `отклонен` через Е, без «ё».**
Сравнение статусов литералами в нескольких местах фронта уже стоило двух раундов «правки не
видно»: отказавший шаг молча выпадал из правки маршрута. Во фронте статусы вынесены в
константы (`request-card.tsx`), сверять надо с этим списком.

Правка маршрута доступна сотруднику ОК/администратору (блок `request_create`) и только в
статусах «Черновик»/«На доработке». Шаги в правке: порядок кнопками «вверх»/«вниз», удаление,
добавление группы селектом и сотрудника — модалкой выбора в AD (логин руками не набирается:
опечатка дала бы шаг, который никто не отметит). Причина отказа и возврата обязательна всегда —
сервер не примет решение без неё (`_check_comment`), независимо от `require_comment` шага.

## 2.1 Справочник шагов (`step_catalog`, миграция 0018)

Переиспользуемые заготовки шага бланка (поля те же, что у `blank_steps`): код (уникален, неизменен),
`title`, `stage_lines`, `executor_kind`, `assignees`, `owner_group`, `approval_mode`, `optional`,
`require_comment`, `active` (шаг недоступен для набора, но остаётся в справочнике).

Срока у заготовки **нет**: `step_catalog.ttl_hours` не существует, в справочнике шагов поля срока
нет — срок задаётся в составе бланка (вкладка «Бланки», см. §2). Копия шага из справочника
получает общий срок `approval_ttl_days`, дальше его можно задать в бланке.

Бланк набирается из справочника **копией**: в составе бланка кнопка «Взять из справочника» кладёт
копию шага в `blank_steps`, после чего шаг правится в бланке независимо (правка справочника уже
собранные бланки не меняет). Редактор справочника — админ-вкладка «Шаги».

Эндпоинты (только `admin`, иначе 403; хранилище недоступно — 503):

| Метод и путь | Назначение |
|---|---|
| `GET /api/settings/routing/step-catalog` | Все шаги справочника, включая отключённые |
| `POST /api/settings/routing/step-catalog` | Создать шаг (код уникален — 409, дубль; группа AD сверяется — 422) |
| `PUT /api/settings/routing/step-catalog/{id}` | Частичная правка (код неизменен) |
| `DELETE /api/settings/routing/step-catalog/{id}` | Удалить шаг (копий в бланках нет — безопасно); нет — 404 |

Аудит: `step_catalog.create`, `step_catalog.update`, `step_catalog.delete`.

## 3. Выбор бланка и снимок в заявке

- `GET /api/requests/route/blanks` — активные бланки для селекта сотрудника ОК (`id`, `code`,
  `name`, `description`, `step_count`, `autopick`).
- `POST /requests/route/preview` и `POST /requests` принимают `blank_id`; в предпросмотре
  приходит снимок бланка (`blank`) и `blank_source`: `chosen` — бланк выбрал ОК, `autopick` —
  подобран по службе.
- Несуществующий или отключённый бланк — 422 со списком доступных бланков.
- В заявку пишется снимок: `blank_id`, `blank_name`, `blank_version`, `blank_header_html`,
  `blank_footer_lines`, а также текст шага, ответственные, режим и признак «шаг можно снять»
  каждого шага (`request_steps`). Правка справочника бланков не меняет уже выданные заявки —
  печать идёт по снимку выданной заявки, как `blank_name`/`blank_version`.
- **Автоподстановка по службе** (`route_profiles` по службе AD) осталась запасным путём и
  выключена: ключ настройки `blank_autopick` (`INFRA_KEYS`, значение `off` по умолчанию, миграция
  0012 сидит `"off"`). Включается только значением `on` (`_blank_autopick_enabled` в
  `api/app/requests.py`).
- Бланк не выбран и `blank_autopick=off` — ОДИНАКОВЫЙ 422 в предпросмотре и при создании: выбрать
  бланк либо задать маршрут вручную, с перечнем доступных бланков (`_blank_required_422`).
- Ручной конструктор ОК (`route_mode=custom`, блоки/группы/сотрудники) не изменился: он работает
  без бланка, бланк в нём необязателен.
- **Бланк при ручном маршруте** (решение человека 2026-10-12): `blank_id` принимается в обоих
  режимах, и снимок бланка (шапка, подвал, название, версия) сохраняется в обоих — печать идёт
  по бланку, даже когда шаги набирает сама ОК. Неизвестный или отключённый бланк — 422 (тихо
  печатать общую форму нельзя); проверка «бланк без шагов» не применяется: в ручном режиме шаги
  задаёт ОК. Переключение режима в форме больше не сбрасывает выбор бланка.
- **Состав блока маршрута** (форма создания, ручной режим): переключателя «тип исполнителя» нет —
  в блоке доступны и добавление сотрудника (модалка выбора в AD), и выбор группы, поэтому блок
  может содержать и людей, и группы вперемешку. Шаг-группа показывается названием из справочника
  (`GET /api/step-groups`), в теле уходит `owner_group`. Порядок шагов внутри блока меняется
  кнопками «вверх»/«вниз» у каждого шага.
- **Обязательные поля при отправке на согласование** (решение человека 2026-10-12): предприятие,
  табельный номер, ФИО и тема. Не обязательны: содержание (API принимает пустую строку), вид
  документа и справочные поля карточки 1С (подразделение, должность — только показываются).
  Перед отправкой форма проверяет заполненность: показывает сводку и подсвечивает поля
  (`aria-invalid`), ввод снимает подсветку поля. Кнопка «Создать» (черновик) требует того же.
- Бланк без шагов выбрать нельзя — 422 с названием бланка и перечнем доступных.

## 4. Несколько ответственных и режим шага (миграция 0013)

| Поле в `request_steps` | Значение |
|---|---|
| `assignees` | jsonb-список логинов ответственных на момент выдачи (один ответственный — список из одного) |
| `assignee` | Первый из `assignees` — обратная совместимость прежнего UI, выборок и писем |
| `approval_mode` | Снимок режима шага; `null` — шаг выдан до миграции, тогда действует `sequential` |
| `approvals` | jsonb-список отметок `[{sam, at, decision, comment}]` — последняя по каждому ответственному |
| `optional` | Снимок признака «шаг можно снять» (миграция 0015): `optional` шага бланка или этапа профиля на момент выдачи |

- Пустой `assignees` — групповой шаг: действует `owner_group` (группа AD), отметку ставит любой
  её участник; печатается колонка группы, ФИО дописывают от руки.
- `sequential` — шаг закрывают все ответственные (`_closes_on_approve`); `parallel` — любая
  отметка. Частичное согласие не двигает заявку и не шлёт письмо, в аудите — `step.approve_partial`.
- Повторная отметка согласия тем же ответственным — 409 («Вы уже согласовали этот шаг»);
  `reject`/`return` действуют сразу от любого ответственного.
- Письмо «назначена» получают все ответственные шага, которые ещё не отметились
  (`mailer.step_logins`/`step_marked_sams`), по одному письму на адресата.

## 5. Печать: что собирается на бланке

`POST /requests/{id}/print` (вариант 1): документ текущего состояния заявки, PDF отдаётся
`pdf_b64` в ответе, версии документов в БД не накапливаются, временные файлы (docx/pdf/qr)
удаляются. Офлайн или нет LibreOffice — `{"generated": false, "reason": ...}`, не 500.

- Единая вёрстка (макета/пресетов нет; поле `blank_layout` снято миграцией 0018). Вид бланка
  службы (`ad_services.blank_kind`) в оформлении не участвует.
- Шапка: `blank_header_html` снимка бланка (если задан — печатается абзацами по `</p>`), иначе
  название бланка (снимок `blank_name`) и поля сотрудника — ФИО, должность, служба, табельный
  номер, предприятие названием из справочника.
- Шаги — таблицей (`docs.STEP_TABLE_HEADERS`): столбцы «№», «Содержание шага»,
  «Ответственные», «Отметка». Содержание: заголовок с режимом жирным + текст `stage_lines`.
  Заголовок (`docs._step_heading`) — название шага, а у **ручного шага** (этапа справочника за
  шагом нет) — должность согласующего из `title_ad` зеркала `users`
  (`documents._fill_step_fio` → `assignee_positions`): «Слесарь (последовательно)». Логин AD
  вместо названия и текста шага не печатается — раньше он выходил дважды («логин (режим) логин»,
  решение человека 2026-10-12); если нет ни названия, ни должности, печатается один режим.
  Ответственные — по строке на каждого: для шага-реестра ФИО по логинам `assignees` из зеркала
  `users`, для **группового шага** — сначала имя группы, затем состав группы AD
  (`documents._fill_step_group_members`, `group_member_names`): иначе сотруднику не к кому
  обращаться (решение человека 2026-10-12). Состав берётся **только из кэша групп**
  (`ad_group_members`, наполняет регламент и кнопка синка): живого чтения AD в печати нет,
  чтобы синхронный запрос не зависел от LDAP-таймаутов. Группы, которой нет в кэше, печатается
  как раньше — одним именем группы. В колонке «Отметка» — статус с датой либо пустая строка под
  росчерк.
  Раскладка **фиксированная** (`w:tblLayout`), ширины столбцов заданы константой
  `STEP_TABLE_WIDTHS_MM` (сумма — 175 мм, полоса набора A4 при полях 20/15 мм): «№» — самая
  узкая, содержание — самое широкое. Таблица печатается ужато: кегль на пункт меньше основного
  текста (`STEP_TABLE_PT`, заголовки внутри текста шага сохраняют свой кегль) и поля ячеек 1 мм
  (`w:tblCellMar`) — типовой бланк укладывается в одну страницу; гарантии для сотни шагов нет.
  Строка заголовков повторяется на следующей странице (`w:tblHeader`), строка шага не
  разрывается (`w:cantSplit`).
- Подвал бланка: строки `blank_footer_lines` снимка по центру после шагов. Строка —
  HTML абзаца визуального редактора, разбирается тем же санитайзером, что шапка
  (`_PRINT_BLOCK_RE` + `_add_stage_text`): абзацы по закрывающему тегу, начертания,
  кегль заголовка и выравнивание редактора; без разметки строка печатается ровно как
  раньше (один абзац по центру). Правило печати подвала — по центру, но выравнивание,
  заданное в редакторе, его переопределяет (как в шапке).
- Подпись страницы: номер заявки, название бланка и его версия (снимок).
- QR — на URL заявки из `APP_BASE_URL`. Печатается **только** на месте плейсхолдера `{qr}` в
  шапке (`docs._add_qr_inline`); отдельного блока QR после шапки больше нет — он ломал вёрстку
  (решение человека 2026-10-12). Бланк без `{qr}` в шапке печатается без QR. Вне шапки `{qr}`
  не разворачивается и остаётся текстом.
- ПДн (отпуск и др.) в бланк не попадают (`sanitize_context`, `FORBIDDEN_CONTEXT_FIELDS`).
- Разметка редактора: `b/strong`, `i/em`, `u`, списки, `br/p/li` — как раньше; заголовки
  `h1`–`h3` печатаются жирным абзацем увеличенного кегля, выравнивание по центру/право
  доходит до абзаца. Из HTML читается только `text-align`: цвет, шрифт, кегль и ссылки на бланок
  не попадают. Учтите: в уже сохранённых шапках бланков встречались `<h1>`–`<h3>` (набор через
  input-rule `# `) — раньше они печатались базовым кеглем, теперь жирным уменьшенным.
- Пустые шаги — 422 («В заявке нет шагов маршрута: бланк печатать нечего»).

### Плейсхолдеры печати

Набор задан решением человека, подставляется в **шапку, подвал и текст шага**
(`docs.blank_placeholders`/`render_blank_text`, список кнопок вставки — `BLANK_PLACEHOLDERS`
в `admin-settings.tsx`):

| Плейсхолдер | Значение |
|---|---|
| `{fio}` | ФИО сотрудника заявки |
| `{position}` | Должность |
| `{department}` | Подразделение (служба) |
| `{tab_num}` | Табельный номер |
| `{enterprise}` | Предприятие названием из справочника |
| `{blank_name}` | Название бланка (снимок) |
| `{subject}` | Тема заявки |
| `{content}` | Содержание заявки |
| `{date}` | Дата печати (`ДД.ММ.ГГГГ`) |
| `{dismissal_date}` | Дата увольнения из кадровых данных — читается по ключу заявки (предприятие+база+табельный номер) по строке СПЕЦИАЛЬНОГО сотрудника, включая уже уволенного |
| `{steps}` | «количество шагов: N» (по шагам заявки) |
| `{manager}` | ФИО руководителя из зеркала AD `users` (карточка сотрудника → `manager_dn` → логин → ФИО) |

Отдельно, **только в шапке**: `{qr}` (`docs.QR_PLACEHOLDER`) — печатает QR-картинку на месте
плейсхолдера; кнопка вставки есть только у шапки (`PlaceholderButtons additional`). Допускаются
пробелы внутри: `{ qr }`. В подвале и тексте шага `{qr}` не подставляется и остаётся текстом.
Печатается QR только по этому плейсхолдеру: у бланка без `{qr}` в шапке QR на листе не будет —
если скан обязателен (`require_paper_signature`), плейсхолдер должен быть в шапке бланка.

Дважды повторённые скобки (`{{ ... }}` из шаблонов писем) печати не касаются. Значения
**экранируются** — `{content}`/`{subject}` печатаются текстом, а не разметкой бланка. Неизвестный
плейсхолдер остаётся текстом: опечатка в бланке — не сбой печати. Нет данных (зеркало недоступно,
дата не разобралась) — пустая строка, печать не падает.

### Задел: варианты таблицы шагов (на будущее)

Сейчас у бланка ровно одна таблица шагов — набор столбцов зашит в печать
(`docs.STEP_TABLE_HEADERS`/`STEP_TABLE_WIDTHS_MM`). Свободный конструктор вёрстки не делается
(ломает серверную печать); когда понадобится документ с другим составом столбцов, вариант
выбирается из закрытого справочника: один и тот же серверный рендер, набор столбцов и подписи —
из настройки, ширины — по тем же ограничениям (сумма ≤ 175 мм). До появления реальной потребности
в коде варианта нет: ни поля в БД, ни ветвления в `docs.py`.

### Предпросмотр «как в печати» в редакторе бланка

В карточке бланка (вкладка «Бланки») есть макет печати (`frontend/src/blank-preview.tsx`):
шапка → блоки шагов (№, название с режимом, текст, ответственные, отметка) → подвал, с
подстановкой плейсхолдеров. Это **МАКЕТ, а не документ**: он подписан в интерфейсе как
приблизительный, потому что документ собирает сервер при печати заявки.

- Показаны только значения, известные клиенту: `{blank_name}`, `{steps}`, `{date}` (сегодняшняя),
  и `{qr}` в шапке — подписью `[QR-код]` (печать вставит картинку).
  Остальные (`{fio}`, `{position}`, `{department}`, `{tab_num}`, `{enterprise}`, `{subject}`,
  `{content}`, `{dismissal_date}`, `{manager}`) известны только заявке — в макете они остаются
  текстом, как и в печати.
- Разметка редактора показывается текстом (без служебных тегов): начертания, кегль, переносы,
  разбивку по страницам и картинку QR макет не воспроизводит. Ответственные показаны
  логинами AD (ФИО подставляет сервер), у группового шага — группа AD, у шага руководителя —
  пометка, что ФИО знает сервер.

## 6. Письма (`mail_templates`)

Настройка `settings.mail_templates` (ключ контента) — список `{code, subject, body_html}`.
`code` — событие: `assigned` (назначена), `reminder`, `escalation`, `returned`, `closed`
и т.д. (см. `mailer.py`). Подстановка — Jinja-синтаксис `{{ имя }}`; неизвестная переменная даёт
пустую строку (ошибкой не считается).

| Переменная      | Значение                                    |
|-----------------|---------------------------------------------|
| `{{ request_id }}` | Номер заявки                              |
| `{{ fio }}`        | ФИО сотрудника                            |
| `{{ url }}`        | Ссылка на заявку (переход из письма)      |
| `{{ comment }}`    | Комментарий последнего действия, изменившего статус заявки (отказ или возврат) — в письме «возврат» автору и в письме «назначена» переоткрытому блоку; в остальных письмах (напоминание, эскалация) — пустая строка |
| `{{ event }}`      | Код события (служебное)                    |

Пример:

```
Тема: Назначена {{ request_id }}
Тело: Заявка {{ request_id }} назначена вам на согласование.
      Сотрудник: {{ fio }}.
      Открыть: {{ url }}
```

Тема письма берётся ТОЛЬКО из поля `subject` шаблона — адрес отправителя в тему не
подставляется (он живёт в заголовке `From`: «Имя <адрес>», имя — инфра-ключ
`smtp_from_name`, пусто — голый адрес; тема строкового легаси-шаблона — «Заявка <номер>»).

Значение `{{ comment }}` подставляется **текстом**: HTML в комментарии экранируется
(свободный текст согласующего не должен стать разметкой письма).

## 7. Справочники маршрута (остались в силе)

Маршрут заявки собирается по справочникам (миграция 0008), а не по текстовым шаблонам:

- `ad_services` — службы (`dept_name` из AD, активность, `blank_kind` — прежний признак вида
  бланка, профиль по умолчанию); в выборе оформления печати не участвует (печать единая);
- `approval_stages` — этапы: название, `owner_kind`, `stage_lines`, флаги `optional`/
  `require_comment`, признак печати исполнителя;
- `stage_assignees` — состав этапа для `stage_roster`;
- `route_profiles` + `route_profile_steps` — профили маршрутов по службам и порядок этапов
  (запасной подбор за `blank_autopick`).

Это запасной путь подбора за `blank_autopick` и основа ручного маршрута; в составе бланка они не
участвуют — шаг бланка самодостаточен.

Легаси снято: таблицы `templates`/`template_steps`/`template_filters` после миграции 0008 пустые
(совместимость), ключи настроек `templates` и `position_to_category` удалены из таблицы `settings`
миграцией 0014 вместе с вкладкой «Шаблоны» админки, мёртвые `doc_templates`/`position_sets` —
миграцией 0016. Вкладка «Письма» (редактор писем) в админке осталась.

## Примечания

- Переменные подставляются **без ПДн сверх нужного**: бланк и письмо получают только
  перечисленные поля; ФИО владельцу-согласующему приходит (он участник процесса).
- Менять набор полей бланка и набор ключей настроек можно только вместе с кодом (контракт) —
  см. AGENTS.md §3.
- Этап профиля без состава исполнителей (`stage_roster` с пустым `stage_assignees`) печатается
  с пустой колонкой ответственного и помечается в интерфейсе как заблокированный —
  состав заполняет администратор в справочниках маршрута. У шага бланка такой настройки нет:
  согласующих задаёт сам шаг (`assignees`).
