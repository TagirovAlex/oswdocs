# Бланки, этапы и письма СЭД: как устроено и что уходит в печать

Обновлено: 2026-10-08. Источник истины — код (`api/app/requests.py`, `api/app/routing.py`,
`api/app/routing_store.py`, `api/app/settings_routes.py`, `api/app/documents.py`, `api/app/docs.py`,
`api/app/mailer.py`) и миграции `db/alembic/versions/0012_blank_directory.py`,
`0013_multi_assignee_steps.py`.

Ключевая мысль модели: **оформление бланка — не файл, а данные**. Файлы-шаблоны `.docx`
(`office.docx`/`line.docx` и производные) удалены из проекта, настройки `doc_templates`/
`position_sets` и их ручки тоже. Документ печати собирается из заявки и снимка бланка.

## 1. Бланк (справочник `blanks`, миграция 0012)

Бланк — элемент справочника заявок. Его выбирает сотрудник ОК при создании заявки; бланк
задаёт состав шагов и ответственных.

| Поле        | Значение                                                        |
|-------------|-----------------------------------------------------------------|
| `code`      | Код бланка (`^[a-z][a-z0-9_]*$`, уникален; дубль — 409)          |
| `name`      | Наименование бланка (видно сотруднику ОК в селекте)             |
| `doc_type_code` | Вид документа (`doc_types.code`) — классификация, на печать не влияет |
| `description` | Пояснение для сотрудника ОК (подсказка селекта)              |
| `layout`    | Макет печати: `office` или `line` (два встроенных пресета)       |
| `active`    | `false` — бланк вне формы заявки (админка его правит, ОК не видит) |
| `version`   | Счётчик состава: растёт при каждой замене шагов                  |

Сид миграции: каждый вид документа `doc_types` становится бланком с тем же кодом и названием,
`layout='office'`. Перенос состава шагов из профилей маршрута НЕ выполняется (у профилей привязка
к службам AD, у бланка — к виду документа) — состав собирает администратор.

Эндпоинты справочника (только `admin`, иначе 403; хранилище недоступно — 503):

| Метод и путь | Назначение |
|---|---|
| `GET /api/settings/routing/blanks` | Все бланки, включая отключённые; в каждой строке `step_count` |
| `POST /api/settings/routing/blanks` | Создать бланк (код уникален) |
| `PUT /api/settings/routing/blanks/{blank_id}` | Частичная правка (код неизменен) |
| `GET /api/settings/routing/blanks/{blank_id}/steps` | Состав шагов по порядку вместе с текстом этапа |
| `PUT /api/settings/routing/blanks/{blank_id}/steps` | Полная замена состава одной транзакцией, `version` растёт |

Аудит: `blank.create`, `blank.update`, `blank.steps.update`.

## 2. Шаг бланка (`blank_steps`, миграции 0012/0013)

Шаг бланка ссылается на этап справочника (`approval_stages.id`); порядок уникален внутри бланка
(в БД это PK `(blank_id, step_order)`, дубль порядка — 422 на границе).

| Поле шага бланка | Значение |
|---|---|
| `stage_id` | Этап справочника; этап вне маршрутов (`active=false`) или несуществующий — 422, состав не меняется |
| `step_order` | Порядок шага в бланке, с 1 |
| `optional_override` | Этап необязательный именно в этом бланке; `null` — как в этапе |
| `require_comment_override` | Комментарий обязателен именно в этом бланке; `null` — как в этапе |
| `approval_mode` | Режим шага: `sequential` («все ответственные», по умолчанию) или `parallel` («любой ответственный») |

Текст шага и вид исполнителя берутся из этапа, а не из бланка:

- `title`, `stage_lines` (пункты этапа) — из `approval_stages`; в админке правится визуальным
  редактором (`frontend/src/rich-text.tsx`, TipTap), HTML уходит в те же поля и доходит до печати;
- `owner_kind` — `ad_group` (группа AD), `manager_ad` (руководитель сотрудника из AD),
  `stage_roster` (состав этапа);
- состав ответственных `stage_roster` — `stage_assignees`; пустой реестр помечает этап
  заблокированным («Не задан состав этапа»).

## 3. Выбор бланка и снимок в заявке

- `GET /api/requests/route/blanks` — активные бланки для селекта сотрудника ОК (`id`, `code`,
  `name`, `description`, `layout`, `step_count`, `autopick`).
- `POST /requests/route/preview` и `POST /requests` принимают `blank_id`; в предпросмотре
  приходят снимок бланка (`blank`, либо прежнее значение `office`/`line` из справочника служб при
  подборе по службе) и `blank_source`: `chosen` — бланк выбрал ОК, `autopick` — подобран по службе.
- Несуществующий или отключённый бланк — 422 со списком доступных бланков.
- В заявку пишется снимок: `blank_id`, `blank_name`, `blank_version`, `blank_layout`, а также
  текст этапа, ответственные и режим каждого шага (`request_steps`). Правка справочника бланков
  не меняет уже выданные заявки.
- **Автоподстановка по службе** (`route_profiles` по службе AD) осталась запасным путём и
  выключена: ключ настройки `blank_autopick` (`INFRA_KEYS`, значение `off` по умолчанию, миграция
  0012 сидит `"off"`). Включается только значением `on` (`_blank_autopick_enabled` в
  `api/app/requests.py`). Бланк не выбран, автоподстановка выключена и справочник не пуст —
  422 «Выберите бланк».
- Ручной конструктор ОК (`route_mode=custom`, блоки/группы/сотрудники) не изменился: бланк в нём
  необязателен.

## 4. Несколько ответственных и режим шага (миграция 0013)

| Поле в `request_steps` | Значение |
|---|---|
| `assignees` | jsonb-список логинов ответственных на момент выдачи (один ответственный — список из одного) |
| `assignee` | Первый из `assignees` — обратная совместимость прежнего UI, выборок и писем |
| `approval_mode` | Снимок режима шага; `null` — шаг выдан до миграции, тогда действует `sequential` |
| `approvals` | jsonb-список отметок `[{sam, at, decision, comment}]` — последняя по каждому ответственному |

- Пустой `assignees` — групповой шаг: действует `owner_group` (группа AD), отметку ставит любой
  её участник; печатается колонка группы, ФИО дописывают от руки.
- `sequential` — шаг закрывают все ответственные (`_closes_on_approve`); `parallel` — любая
  отметка. Частичное согласие не двигает заявку и не шлёт письмо, в аудите — `step.approve_partial`.
- Повторная отметка согласия тем же ответственным — 409 («Вы уже согласовали этот шаг»);
  `reject`/`return` действуют сразу от любого ответственного.
- Письмо «назначена» получают все ответственные шага, которые ещё не отметились
  (`mailer.step_logins`/`step_marked_sams`), по одному письму на адресата.

## 5. Печать: что собирается на бланке

`POST /requests/{id}/print` (вариант 1): документ текущего состояния заявки, PDF отдаётся
`pdf_b64` в ответе, версии документов в БД не накапливаются, временные файлы (docx/pdf/qr)
удаляются. Офлайн или нет LibreOffice — `{"generated": false, "reason": ...}`, не 500.

- Макет — из снимка `blank_layout` (`office` по умолчанию, `resolve_blank_layout`); два встроенных
  пресета `docs.LAYOUT_PRESETS` (поля страницы, кегль, сторона QR, заливка шапки, доли колонок).
  Вид бланка службы (`ad_services.blank_kind`) в выборе оформления не участвует.
- Шапка: название бланка (снимок `blank_name`) и поля сотрудника — ФИО, должность, служба,
  табельный номер, предприятие названием из справочника.
- Таблица шагов: №, этап (название и пункты `stage_lines`), ответственные (`assignee_names` —
  ФИО по логинам `assignees` из зеркала `users`, по строке на ответственного), отметка/дата.
- QR — на URL заявки из `APP_BASE_URL`.
- Подвал — номер заявки, название бланка и его версия (снимок).
- ПДн (отпуск и др.) в бланк не попадают (`sanitize_context`, `FORBIDDEN_CONTEXT_FIELDS`).
- Пустые шаги — 422 («В заявке нет шагов маршрута: бланк печатать нечего»).

## 6. Письма (`mail_templates`)

Настройка `settings.mail_templates` (ключ контента) — список `{code, subject, body_html}`.
`code` — событие: `assigned` (назначена), `reminder`, `escalation`, `returned`, `closed`
и т.д. (см. `mailer.py`). Подстановка — Jinja-синтаксис `{{ имя }}`; неизвестная переменная даёт
пустую строку (ошибкой не считается).

| Переменная      | Значение                                    |
|-----------------|---------------------------------------------|
| `{{ request_id }}` | Номер заявки                              |
| `{{ fio }}`        | ФИО сотрудника                            |
| `{{ url }}`        | Ссылка на заявку (переход из письма)      |
| `{{ event }}`      | Код события (служебное)                    |

Пример:

```
Тема: Назначена {{ request_id }}
Тело: Заявка {{ request_id }} назначена вам на согласование.
      Сотрудник: {{ fio }}.
      Открыть: {{ url }}
```

## 7. Справочники маршрута (остались в силе)

Маршрут заявки собирается по справочникам (миграция 0008), а не по текстовым шаблонам:

- `ad_services` — службы (`dept_name` из AD, активность, `blank_kind` — прежний признак вида
  бланка, профиль по умолчанию); макет печати теперь задаёт бланк, а не служба;
- `approval_stages` — этапы: название, `owner_kind`, `stage_lines`, флаги `optional`/
  `require_comment`, признак печати исполнителя;
- `stage_assignees` — состав этапа для `stage_roster`;
- `route_profiles` + `route_profile_steps` — профили маршрутов по службам и порядок этапов
  (запасной подбор за `blank_autopick`).

Прежние `settings.templates`/`template_steps`/`template_filters` в подборе не участвуют: после
миграции 0008 это пустые таблицы (совместимость). Ключи настроек `doc_templates`/`position_sets`
удалены из контракта вместе с файлами-шаблонами.

## Примечания

- Переменные подставляются **без ПДн сверх нужного**: бланк и письмо получают только
  перечисленные поля; ФИО владельцу-согласующему приходит (он участник процесса).
- Менять набор полей бланка и набор ключей настроек можно только вместе с кодом (контракт) —
  см. AGENTS.md §3.
- Этап без состава исполнителей (`stage_roster` с пустым `stage_assignees`) печатается
  с пустой колонкой ответственного и помечается в интерфейсе как заблокированный —
  состав заполняет администратор в справочниках маршрута.
