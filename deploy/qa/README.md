## 1. Матрица ролей (playwright)

### Установка

Playwright ставится один раз на машине прогона (на ВМ или с машины QA через VPN):

```bash
npm init -y
npm install -D @playwright/test
npx playwright install chromium
```

### Переменные окружения (секреты — только env, не в коде)

```bash
export SED_BASE_URL=https://sed.company.local
export LOGIN_ADMIN=...   PASS_ADMIN=...
export LOGIN_HR=...      PASS_HR=...
export LOGIN_HR_ADMIN=... PASS_HR_ADMIN=...
export LOGIN_OWNER=...   PASS_OWNER=...
```

Учетки — реальные доменные из групп `SED_ADMINS`, `SED_HR`, `SED_HR_ADMIN`,
`SED_STEP_EXEC` (или группы шага). Учетка не задана в env — тест роли пропускается (skip).

### Запуск

```bash
npx playwright test roles-matrix.spec.ts --reporter=line
```

### Что покрывает (README п.1 «Поиск/доступ» и матрица ролей)

Вкладки — строго как в `layout.tsx` (`visibleTabs`): «Заявки» и **«Заместители» есть у
всех вошедших без блоков прав** («Заместители» — личный раздел сотрудника, решение
человека 2026-10-15), дальше по блокам из `/auth/me`: «Справочник» —
`employee_directory`, «Сопоставление» — `link_match`, «Настройки» —
`settings_content`/`settings_infra`. Отдельной вкладки «Создание» в каркасе нет:
создание заявки открывает кнопка «Создать заявку» (окно `?view=create`).

| Роль | Вкладки (layout.tsx) | Создание | Настройки | Карточка |
|------|----------------------|----------|-----------|----------|
| admin | Заявки / Заместители / Справочник / Сопоставление / Настройки | кнопка «Создать заявку» | форма + `GET /api/settings` 200 (всё) | полные колонки с ПДн |
| hr_admin (руководитель ОК) | Заявки / Заместители / Справочник / Настройки | кнопка «Создать заявку» | только контент: `GET /api/settings/content` 200, `GET /api/settings` 403 | полные колонки с ПДн |
| hr | Заявки / Заместители / Справочник | кнопка «Создать заявку» | вкладки нет, `GET /api/settings*` 403 | полные колонки с ПДн |
| owner | Заявки / Заместители | вкладки нет | вкладки нет, API 403 | `tab_num/enterprise/employee_key=null`; `fio` и `department` видны всем (решение человека 2026-10-14), маска «Сотрудник № …» — только на заявках без ФИО; видны заявки по правилу участия (см. ниже) |
| sed_admin (администратор СЭД) | по блокам прав (после «Заместители») | по блокам прав | как у роли с блоком настроек | полные колонки с ПДн (роль привилегированная, `deps.is_privileged`) |
| guest | нет (экран логина) | нет | `GET /api/*` → 401 | данных нет |

Отдельно проверяется: число кнопок в `<nav aria-label="Вкладки">` ровно «вкладки +
кнопка темы + Выйти» (лишних вкладок нет и порядок совпадает с `visibleTabs`), ПДн
владельцу не отдает API (не только скрывается в UI).

### Заместители: две точки входа в один справочник (стенд)

| Роль | Личная вкладка «Заместители» (без блоков прав) | Админский справочник в настройках (блок `settings_substitutes`) | Подбор заместителя |
|------|----------------------------------------------|------------------------------------------------------------|-------------------|
| admin / sed_admin | есть | есть, весь справочник | `GET /api/substitutes/candidates` 200 |
| hr / hr_admin / owner | есть | вкладки нет, `GET /api/settings/substitutes` → 403 | `GET /api/substitutes/candidates` 200 |

1. Вкладка «Заместители» видна **любому вошедшему** сразу после «Заявки» и открывает
   раздел «Мои заместители» без блоков прав; `GET /api/substitutes/my` → 200,
   `GET /api/settings/substitutes` → 403 у сотрудника без блока.
2. Подбор заместителя идёт из локального справочника сотрудников, а не из живого AD:
   `GET /api/substitutes/candidates?q=…&page=…&page_size=…` → `{items, total, page,
   page_size}`, в элементе `sam`/`fio`/`department`/`position`, себя самого не
   возвращает. `q` короче 2 символов — **422**.
3. Границы личных ручек: чужую запись по id не отдают и не правят — **404** (не
   403/409, иначе по коду ответа видно, что запись существует); `principal_sam` в
   теле личной ручки — **422** (логин оригинала всегда из сессии); заместитель «сам
   себе» — **422**.
4. **Справочник сотрудников и поиск в живом AD — по блоку `employee_directory`**:
   у роли без него нет вкладки «Справочник», а `GET /api/ad/search?q=…` → **403**
   (у `hr`/`hr_admin`/админ блок есть — 200). `/api/employees` гейтом блока не
   закрыта, но требует `enterprise` и без привилегированной роли отдаёт справочник
   **без ФИО и табельного номера** (`dept`/`position`/`ad_sam`/`ad_status`).
   Новой видимости ФИО это не отменяет: подбор заместителя идёт по локальной таблице
   и отдаёт ФИО сотрудников всем вошедшим в объёме
   `sam`/`fio`/`department`/`position` (решение человека 2026-10-15) — других ручек
   новая видимость не касается.
5. Админ в настройках по-прежнему правит **весь** справочник — обе точки правды в одну
   таблицу `substitutes`.
6. **Лимит заместителей** — инфраструктурная настройка `substitute_deputies_limit`
   (дефолт 3, вкладка «Инфра», сид — миграция 0025). Проверка: при дефолте первые три
   действующие на сегодня записи проходят, **четвёртая — 422** с именем ключа
   настройки в тексте (на всех четырёх ручках записи: `POST/PUT /api/substitutes/my`
   и `POST/PUT /api/settings/substitutes`); истёкшие и ещё не начавшиеся записи место
   не занимают; правка записи при полном лимите проходит (себя в счёт не считает).
   У админа поле «Лимит заместителей» видно на вкладке «Инфра», у личного раздела
   «Заместители» — нет.

### Карточка заявки: правило участника (стенд)

Правило видимости — не «только владелец шага», а участие в согласовании (решение
человека 2026-10-15): карточку видят инициатор, владелец шага и тот, кто уже
согласовал, даже если сотрудник ОК потом переназначил его шаг. Точки проверки:

1. `GET /api/requests` (вкладка «мои») и счётчик папки «Мои задачи» считают одно и то
   же — список и дерево не расходятся.
2. Посторонний (не инициатор, не ответственный, не отметившийся) — карточка **403**, и
   в «моих» у него **пустой список**.
3. `sed_admin`: карточка **200** (привилегированный), бланк `GET /api/documents/{id}` —
   **403**, вложения — **403**. Расширялось участие в согласовании, а не роли.
4. ПДн **в карточке** у участника обрезаны как прежде: `tab_num`/`enterprise`/
   `employee_key` = null, `fio` и `department` видны (решение человека 2026-10-14).
   Оговорка: обрезка относится к карточке. **Бланк — это ПДн** (ФИО, табельный
   номер, предприятие, должность, данные об отпуске), и `GET /api/documents/{id}/pdf`
   отдаёт файл всем участникам согласования — решение человека 2026-10-15. Проверять
   надо и это: участник должен открыть бланк и скачать PDF.

## 2. Полнота audit_log

После прогона ролевых сценариев:

```bash
psql "$DATABASE_URL" -f audit-fullness.sql
```

Проверяет: счётчики (всего/за сутки/за 24ч), события за день по `action`,
топ-акторов, отсутствие событий без `actor`, разбивку по сущностям,
append-only (UPDATE любой записи и DELETE истории **живой** заявки обязаны
падать — триггер; при этом след уже удалённой заявки удаляется, п.6б),
полноту ключевых `action` за день. Пустая строка п.7 — действие не
аудируется (дыра полноты).
П.6б — единственная часть скрипта, которая пишет: создаёт пробную запись
в `audit_log` с номером, которого нет среди живых заявок, и удаляет её
(INSERT+DELETE в одном блоке = ноль изменений; при ошибке psql откатит всё).

## 3. НФТ — nft-checklist.md

Чек-лист закрывается вручную/скриптами перед приемкой Фазы 6: TLS 1.2+/HSTS,
сессии 15–20 мин, rate-limit логина (Redis), RPO 24ч/RTO 4ч, ПДн по ролям.

## 4. Сопоставление 1С↔AD и кадровые данные (стенд)

Раздел «Сопоставление» (admin) — ручной сценарий:

1. `POST /api/link_1c_ad/sync` (кнопка «Запустить сопоставление») → сводка прохода:
   `scanned`, `created`, `skipped_*`, `skipped_dismissed`, счётчики расхождений.
2. `GET /api/link_1c_ad/discrepancies?reason=…` → строки расхождений, у каждой видно
   кандидата AD (логин, ФИО, служба, должность), должность/службу карточки 1С и
   прочие табельные номера группы.
3. `POST /api/link_1c_ad/discrepancies/confirm` пачкой → `linked/skipped/errors`;
   неоднозначные строки (`ad_duplicate`) в пакет не попадают, выбор — вручную.
4. Проверка, что после подтверждения `POST /api/requests/route/preview` возвращает
   `link_state=linked`, профиль подобран, а этап руководителя не заблокирован
   (у кого в AD нет атрибута `manager` — блокируется, это данные).

Бланки, шаги и снятие шага (стенд, админ + сотрудник ОК):

1. `GET /api/settings/routing/blanks` — справочник; у каждого `step_count`.
2. Состав шагов — собственные шаги бланка: `GET/PUT /api/settings/routing/blanks/{id}/steps`
   (название, текст, `executor_kind` people/ad_group/manager_ad, согласующие, режим шага,
   `optional`/`require_comment`; этап справочника не указывается). Там же — шапка `header_html`
   и подвал `footer_lines` бланка.
3. Снятие шага бланка — по номеру: `POST /api/requests/route/preview` с `blank_id` и
   `dismissed_step_orders`. Негативные случаи — 422: номер вне состава маршрута (в перечне),
   номер у обязательного шага (с номером и названием), сняты все шаги. Снятие этапов профиля
   службы/ручного маршрута осталось по кодам (`dismissed_stages`).
4. Бланк не выбран при `blank_autopick=off` — одинаковый 422 в предпросмотре и в `POST /requests`
   с перечислением вариантов; `route_mode=custom` (`blocks`/`steps`) работает без бланка; бланк
   без шагов выбрать нельзя (422).

Кадровые данные:

- `POST /api/employees/sync` — заполняет справочник и `ref_key`; `POST /api/employees/hr-sync`
  — проход по регистру кадровых данных (даты увольнения). Оба — admin.
- Регламенты (worker): `schedule_hr_dismissals_sync` (кадровые данные), `schedule_ad_links_sync`
  (сопоставление), `schedule_enterprises_sync`, `schedule_ad_groups_sync` — в настройках,
  метки `hr_dismissals_synced_at`/`ad_links_synced_at` пишутся только после успеха.
- Проверка: уволенные (`dismissal_date <= сегодня`) не выдаются в `GET /api/employees`
  и не участвуют в сопоставлении; уволенный с AD-учёткой тоже скрыт.

Только чтение AD/1С: запись — исключительно в локальную БД (`link_1c_ad`, `users`,
`employee_base_map`, `employees`, `link_discrepancies`).

## 5. Что проверяется ВРУЧНУЮ (не автоматизировано)

- **Печать бланка PDF/QR** (`POST /api/requests/{id}/print`): документ собирается из данных заявки
  (python-docx) единой вёрсткой (макета/пресетов нет) и конвертируется в PDF через LibreOffice,
  QR с ссылкой на заявку. Шапка и подвал — из снимка (`blank_header_html`/`blank_footer_lines`),
  каждый шаг — отдельным блоком строк (заголовок с режимом «последовательно/параллельно», текст,
  «Ответственный: …» — ФИО всех ответственных шага, «Отметка/дата: …»). Плейсхолдеры
  шапки/подвала/шага подставляются:
  `{fio}`, `{position}`, `{department}`, `{tab_num}`, `{enterprise}`, `{blank_name}`, `{subject}`,
  `{content}`, `{date}`, `{dismissal_date}`, `{steps}`, `{manager}`; значения печатаются текстом,
  неизвестный плейсхолдер остаётся текстом. PDF отдаётся `pdf_b64`, версии не накапливаются,
  временные файлы удаляются. Проверка — печать на обычном принтере, внешний вид.
- **Почта (SMTP Exchange)**: письма `назначена → напоминание → эскалация → просрочка →
  закрыта/возврат` из `mail_templates`; доставка на `mail` из AD, у шага с несколькими
  ответственными — всем, кто ещё не отметился.
- **Сканы-вложения**: загрузка, лимиты `scan_max_mb`/`scan_retention_days`,
  ошибки 413/415/409.
- **Эскалация и просрочка TTL** — через worker по расписанию. Просрочка статусов
  не меняет: заявка остаётся «На согласовании», письмо `overdue` уходит ответственным
  за просроченный шаг и их руководителю (одно на круг согласования — номер шага и его
  срок в метке дедупликации), в карточке истёкший срок выделен цветом; шаг остаётся
  «ожидает», отметка принимается (решение человека 2026-10-17).
- **Резервное копирование** — `pg_dump` + снапшот (см. `deploy/LAYOUT.md`).
